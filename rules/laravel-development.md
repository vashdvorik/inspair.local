# Правила разработки под Laravel

Свод правил для проектов на Laravel (монолит, API, пакеты). Основываемся на официальных рекомендациях и внутренних требованиях к безопасности, поддерживаемости и качеству.

## Базовые принципы
- PHP 8.1+ и актуальные зависимости; избегайте устаревших API.
- Соблюдайте слои: домен/приложение/инфраструктура/интерфейсы (HTTP/Console). Не тяните транспорт/ORM в домен без абстракций.
- Контроллеры тонкие: валидация через FormRequest/Validator, авторизация через Policies/Gates, бизнес-логика в сервисах/доменных классах.
- Настройки и секреты — только через `.env` и `config/**`; никакого хардкода.
- Локализация через `lang/**`, `__()` и Blade-директивы; не прошивайте строки в коде.
- Любой код сопровождайте тестами/статиками: PHPUnit (artisan test), PHPStan/Larastan, Pint/фиксер, опционально Deptrac.

## Работа с данными
- Используйте Eloquent/Query Builder с явными моделями и связями. Указывайте `$fillable`/`$guarded`, скрывайте чувствительные атрибуты (`$hidden`, casts).
- Избегайте N+1: применяйте eager loading (`with`, `load`) по умолчанию для связей, используйте `lazyById`/пагинацию для больших выборок.
- Все мутации, затрагивающие несколько сущностей, оборачивайте в транзакции (`DB::transaction`).
- Миграции идемпотентны, содержат индексы/ограничения, соответствуют модели данных; сидеры и фабрики обновляйте вместе с миграциями.
- Не храните чувствительные данные в открытом виде — используйте шифрование/хеширование по назначению.

## Безопасность и доступ
- Проверяйте аутентификацию и авторизацию для всех действий; используйте Policies/Gates, middleware (`auth`, `can`, rate limiting).
- Формы и API: валидируйте входные данные (типизация, правила, кастомные сообщения), экранируйте вывод в Blade, включайте CSRF для форм, проверяйте CORS для API.
- Rate limiting и защита от брутфорса для публичных эндпоинтов; ведите аудит важных операций через логи/события.
- Не логируйте секреты, токены и PII; конфигурируйте маскирование чувствительных полей в логах.

## Архитектура и интеграции
- Сервисы и доменные операции оформляйте как классы/handlers/use-cases; выносите интеграции во внешние клиенты (HTTP, MQ) с интерфейсами.
- Используйте события/слушатели и очереди для асинхронных задач; конфигурируйте retry/timeout/backoff.
- Не завязывайтесь на конкретный транспорт: отделяйте HTTP/Console от ядра приложения.
- Для пакетов используйте service providers, публикуемые ресурсы и конфиги; тестируйте через `orchestra/testbench`.

## Кэш и производительность
- Применяйте кэш/Redis, где есть частые чтения; инвалидируйте кэш при изменениях данных.
- Оптимизируйте запросы: выборка нужных полей (`select`), индексы в миграциях, пагинация/seek.
- Поддерживайте `config:cache`, `route:cache`, `view:cache` в prod (учитывайте совместимость с динамическими значениями).

## Код и стиль
- Соблюдайте PSR-12 или Pint-пресет; включайте `declare(strict_types=1);` во все PHP-файлы.
- Пишете читаемые имена классов/методов/переменных, избегайте магических чисел; выносите константы в конфиги/enum/ValueObject.
- Стремитесь к явной типизации, используйте DTO/Value Objects вместо массивов, где это повышает читаемость.

## Тесты и качество
- Минимальный набор: `php artisan test`, `vendor/bin/phpstan` (larastan), `vendor/bin/pint --test` или фиксер (dry-run). Deptrac — по необходимости.
- Тесты размещайте в `tests/Unit` и `tests/Feature`; для пакетов — через orchestra/testbench.
- Поддерживайте актуальные фикстуры/сидеры для тестов.
